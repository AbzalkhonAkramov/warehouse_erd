# Warehouse ERP — Правила и как это работает

Полный набор правил системы, сосредоточенный на потоке **заказ → фото → доставка**
и на рабочем процессе, от которого он зависит.

---

## 1. Жизненный цикл заказа

**Статусы:** `new (новый) → shipped (отгружен) → delivered (доставлен)`, а также
`refund (возврат)` и `cancelled (отменён)`.

| Правило | Как это работает |
|---|---|
| Заказ начинается как **`new`** | Когда агент (или менеджер от имени агента) создаёт заказ, он открывается в статусе `new`. |
| Меняет статус только **менеджер/админ** | Агенты не могут перемещать заказ. Смена статуса идёт через действие менеджера «Переместить» (`move_order`). |
| **Доставщик** задаётся только пока заказ `new` | Менеджер вписывает имя доставщика; поле блокируется, как только заказ выходит из `new`. |
| Часовой пояс — **Asia/Tashkent** | Все отметки времени, ночная архивация и дата в подписи к фото используют UTC+5. |

**Финансовые последствия перемещения:**
- `new → shipped`/`delivered`: списывает остаток со склада, создаёт счёт-фактуру, увеличивает долг клиента.
- `→ refund` / `→ cancelled`: уменьшает долг. При **возврате** менеджер также выбирает: **вернуть товар на склад** или держать его как **«возвращённый товар»** (отдельный реестр/страница с фильтрами).

**Форкинг (частичные перемещения):**
- Перемещение **всех** позиций перемещает заказ целиком.
- Перемещение **части** позиций **форкает** новый заказ для перемещённых товаров; остаток сохраняет текущий статус.
- Нумерация: обычный заказ — `#15`; форки — `#15.1`, `#15.2`, … Оригинал **сохраняет `#15`** при всех перемещениях.

**Ночная архивация (00:00 Asia/Tashkent):**
- Заказы `delivered`, `cancelled`, `refund` архивируются (исчезают из активного списка).
- **`shipped` никогда не архивируется** (он ещё в работе).
- Смена статуса архивного заказа **разархивирует** его.

## 2. Требование фото / «шлюз» доставки

Это связующее звено между заказами и фотоотчётами.

**Два переключателя определяют, нужны ли фото для заказа:**
- **Переключатель агента «важно»** (`photo_required` у пользователя) — задаёт **админ** в «Аккаунтах», по умолчанию **включён**. Выключен = заказам этого агента фото никогда не нужны.
- **Переключатель заказа** (`photo_required` у заказа) — задаёт **менеджер** в карточке заказа, по умолчанию **включён**. Позволяет менеджеру освободить конкретный заказ от требования.

**Шлюз (итоговое правило):**

> Заказ можно перевести в **`delivered`** только если
> **агент «важный»** И **заказ требует фото** И **для этого заказа в Telegram доставлены фото «до» + «после».**

- Если фото нужны, но отсутствуют → перевод в доставку отклоняется с ошибкой **400** («Перед отметкой о доставке к заказу должны быть прикреплены фото до/после»).
- «Доставлены в Telegram» означает, что у записей изображений есть реальная ссылка Telegram. Отчёт, отправка которого **не удалась, не засчитывается** для шлюза.
- Шлюз применяется только к `delivered` — `shipped` никогда не блокируется.

## 3. Когда агент может отправить фотоотчёт

| Правило | Как это работает |
|---|---|
| **Отчёт, привязанный к заказу → только пока `shipped`** | Отправка фото «до/после» для конкретного заказа разрешена **только когда заказ `shipped`**. Любой другой статус (new, delivered, refund, cancelled) отклоняется с ошибкой **409** («Фотоотчёт можно отправить только пока заказ отгружен»). |
| Доставленные заказы **выпадают** из потока отчётов агента | В мобильном приложении кнопка 📷 *прикрепить* показывается **только для `shipped`** заказов, а в выборе заказа перечислены **только отгруженные** заказы. Поэтому для доставленного заказа отправка отчёта недоступна. |
| **Отчёты без заказа разрешены в любое время** | Агент может отправить отдельный отчёт «до/после» / о состоянии, выбрав **«Без конкретного заказа»** (например, «товара достаточно, заказ не нужен»). У них нет заказа, поэтому правило `shipped` не применяется. |

**Какой поток это создаёт:**
`shipped` → агент отправляет «до/после» → менеджер может перевести заказ в `delivered` (шлюз пройден) → заказ выходит из потока отчётов агента.

**Две точки входа (мобильное приложение):**
1. **Из заказа** — 📷 на отгруженном заказе открывает экран фото с **заранее закреплёнными и заблокированными** магазином и заказом.
2. **Отдельный экран** — выбрать магазин, затем выбрать один из его **отгруженных** заказов (или «Без конкретного заказа»).

## 4. Хранение фото — только в Telegram

| Правило | Как это работает |
|---|---|
| Фото **никогда не хранятся на сервере** | Байты «до/после» сразу пересылаются в Telegram и отбрасываются. Файлы на диск не пишутся. |
| Отправляются **одним альбомом** | «До» и «после» идут **одним сообщением** (медиагруппой), с одной подписью. |
| Менеджеры смотрят через **«Открыть в Telegram»** | У каждого изображения хранится прямая ссылка (`https://t.me/c/<chat>/<thread>/<message>`); в карточке заказа и на странице «Фотоотчёты» вместо миниатюр показываются кнопки **✈ Открыть в Telegram**. |
| **Без повторной отправки** | Так как ничего не хранится, неудавшийся отчёт нельзя переотправить — агент должен отправить новый (эндпоинт переотправки возвращает 409 с этим сообщением). |

**Подпись в Telegram содержит:**
```
📸 Before / After — <название магазина>
Order #<id>            (или «No order»)
Agent: <полное имя>
Date: 01.07.2026 14:35   ← короткая дата + время в 24-часовом формате, Asia/Tashkent
Comment: <заметка агента>
#shop_<название> #user_<имя> #order_<id> #month_<ГГГГ_ММ>
```
- **Хештеги** делают Telegram удобным для поиска по **магазину, пользователю, заказу и месяцу**. У каждого тега сохраняется буквенный префикс (`shop_`, `user_`, `order_`, `month_`), чтобы Telegram делал его кликабельным; имена приводятся к «слагу» (пробелы/пунктуация → `_`), кириллица/узбекские буквы сохраняются, а пустой слаг заменяется на id.
- Отчёты без заказа показывают `No order` / `#no_order`.

**Маршрутизация темы (куда попадает альбом):**
1. Явно выбранная тема, иначе
2. назначенная агенту **тема по умолчанию**, иначе
3. тема с флагом **по умолчанию + активна**.
- Если **активная тема не найдена**, отчёт сохраняется как **FAILED** и ничего не отправляется.

## 5. Видимость и доступ

| Правило | Как это работает |
|---|---|
| Агенты видят **только свои назначенные магазины** | Магазины связаны с агентами (многие-ко-многим). У магазина может быть более одного агента. |
| Менеджеры назначают магазины агентам | Как категории — менеджеры закрепляют магазины за аккаунтами агентов. |
| Менеджеры **всегда видят все магазины** | Для менеджеров/админов ограничений по магазинам нет. |
| Агенты видят **только свои заказы**; менеджеры — все | Каждый заказ несёт информацию о создавшем пользователе, поэтому менеджеры видят, кто его оформил. |
| Магазины сгруппированы по **регионам** и имеют **город** | Менеджеры создают регионы и закрепляют за ними магазины; город — свободный текст, вводимый при создании магазина. |

## 6. Быстрая справка — что блокируется

- Перевод заказа в **`delivered`**, когда фото нужны, но отсутствуют → **блокируется (400)**.
- Отправка отчёта, привязанного к заказу, который **не `shipped`** → **блокируется (409)**.
- Повторная отправка неудавшегося отчёта → **409** (на сервере не хранится).
- Создание отчёта, когда **нет активной темы Telegram** → сохраняется как **FAILED**, ничего не отправляется.
- Заказы в статусе **`shipped`** → никогда не архивируются и не блокируются шлюзом.
